# IPC contract (frontend ↔ backend)

All commands are `#[tauri::command]` in `crates/app/src/commands/`. Types come from
`crates/core/src/ipc_contract.rs` and the core domain, and are generated by ts-rs into
`src/shared/api/ipc.gen.d.ts` via `mise run gen-types`.

Errors: commands return `Result<T, String>`; the string is
`ERR_CODE: message`, where `ERR_CODE` is the `Error::code()` method
(for example `CRYPTO`, `MISSING`, `INVALID_INPUT`, `REQUIRES_UNLOCK`, `NOT_FOUND`,
`SYNC_CONFLICT`).
The frontend parses the code and shows a localized message.

| `sync-error` | `SyncErrorEvent { code, message, peer_name?, peer_version?, own_version? }` | the session did not start or was interrupted: `SYNC_OTHER_VAULT`, `SYNC_VERSION_MISMATCH`, `SYNC_CLOCK_SKEW`, `SYNC_REVOKED`, `SYNC_REJECTED`, `SYNC_CHANNEL`, `SYNC_PAUSED_BY_PEER` and `SYNC_FORGOTTEN_BY_PEER` (the other device paused the exchange or forgot this one; the text names the device, `peer_name`); `SYNC_VERSION_MISMATCH` also has `peer_version` (empty for an old build) and `own_version`: the text names the device and both versions |
| `transfer-receive` | `TransferReceiveView` | a vault receive step: waiting, request, code, progress, done (`saved_path`), error (`SYNC_TRANSFER_EXPIRED`, `SYNC_BAD_CODE`, `SYNC_TRANSFER_DECLINED`, `SYNC_NOT_A_VAULT`) |
| `transfer-send` | `TransferSendView` | a transfer step: waiting for "Accept", the code (`wrong_code`, `attempts_left`), progress, done, error |
| `transfer-nearby` | `TransferNearby[]` | nearby devices waiting to receive |
| `vault-changed` | `VaultStatus` | the vault was locked without a window request (Android: background lock, the button on the sync notification); the window goes to the unlock screen |
| `vault-save-failed` | `string` or `{ reason, exiting }` | the batched vault write failed (it retries by itself); `exiting` — on exit, the window offers "Retry" / "Quit without saving" |
| `vault-saved` | — | a write succeeded again after an error |
| `update-state` | `UpdateStatusDto` | the update check changed phase: checking, downloading (`percent`), ready, available (hand-updated installs), up to date, error |

Background tasks live in `crates/app/src/scheduler.rs`: one thread, a tick every 30 s,
only while the vault is unlocked — Bybit import, automations, alerts (prices of their
assets no more than once in 5 minutes), reminders. System notifications are
`tauri-plugin-notification` (capability `notification:default`).

### sandbox (`crates/app/src/commands/sandbox.rs`, core — `crates/core/src/sandbox`)
The sandbox is a separate temporary vault with 12 months of demo data; everything done in it is erased. It lives in `app_cache_dir()/sandbox/sandbox.wallet` (the release and the dev build each have their own folder), **without a password** (the open variant of the container: demo data is no secret, and a key in memory would cost Argon2 on every open and reset). The seed is deterministic: a fixed seed and ids, the "today" date (UTC) comes as a parameter.

It is erased by: `close_sandbox`, lock, signing in to another vault, quitting the app (`RunEvent::Exit`) and the next start (`setup`, before any open). The path is checked in Rust (`SandboxDir::contains`: canonical, no `..`, no symlinks outward); commands do not accept a path. It does not get into `recent_vaults.json` and does not change `vault_path`. Disabled, the response is `SANDBOX`: sync (does not start), transfer to a device, an external copy, exchange keys and exchange reconciliation, data sources (`datasource_preview/test/refresh` and the background), transaction look-up on the network, system notifications (the window gets them as usual), the snapshot for the lock screen. Automations are computed on demo data.

| Command | Input | Output |
|---|---|---|
| `open_sandbox` | — | `VaultInfo` (`encrypted: false`); the real vault must be locked (otherwise `SANDBOX`); an already open sandbox is recreated |
| `reset_sandbox` | — | `VaultInfo` — clean demo data again; only while the sandbox is open and its file lies in the `sandbox/` folder (otherwise `SANDBOX`) |
| `close_sandbox` | — | `()` — close and erase; `SANDBOX` if the sandbox is not open (the real vault is not touched) |
| `is_sandbox` | — | `bool` |

### updates (`crates/app/src/commands/updates.rs`, logic `crates/app/src/updates.rs`, core `crates/core/src/updates`)

| Command | Input | Output |
|---|---|---|
| `update_status` | — | `UpdateStatusDto { phase, current_version, install_kind, channel, auto_update, last_check }`; `phase` is tagged `type`: `idle` / `checking` / `up_to_date` / `downloading { percent }` / `ready { version }` / `available { offer: UpdateOffer }` / `error { message }` |

AppImage, NSIS/MSI and macOS .app installs download in the background and install on exit; other installs
(deb, rpm, Pacman, Flatpak, Android) only get `available` with a hint. Debug builds read the manifest from
`MWT_UPDATE_URL` when set.

**Edit forms and `base`.** The update inputs of edit forms (`update_store`, `update_transaction`, `update_contact`,
`update_category`, `update_automation`, `update_budget`, `update_goal`, `update_reminder`, `update_price_alert`,
`update_utility_item`, `update_envelope`) take an optional `base`: the version of the entity the form loaded
(`Transaction` / `Store` / `Category` for the first, the form's own input type for the others). When it is set, the core
applies only the fields that differ between `base` and the edit onto the current document (nested objects are merged
per key, arrays and scalars whole), so a change another device synced into a different field while the form was open
is not overwritten with the stale value; when both changed one field, the edit wins. Without `base` the whole input is
applied as before (old frontends, the JSON editor). Nothing in the vault file changes.

### attachments — files and links (`crates/app/src/commands/attachments.rs`)
A file is encrypted with its own random key (XChaCha20-Poly1305, AAD — the attachment id) and lies in `<vault>.files/<id>`; the key is stored in `doc.attachment_keys` inside the encrypted vault and is never handed out. ### shared events (shared spending, get-togethers)

An event is a live list of items; shares, balances, status and debts are **computed** from it and not stored. All mutations answer with a fresh `SharedEventView { event, status (planning|in_progress|settling|closed), totals { planned, spent, diff }, people[{ id, name, kind (me|contact|guest), contact_id?, has_details, is_organizer, share, paid, moved, written_off, saldo, due_at? }], items[{ item_id, cost, qty, plan_total?, plan_qty?, diff_money, diff_qty, bought, shares }], purchases[{ item_id, purchase_id, event_amount, my_part, payment_missing, needs_rate }], settlements[{ settlement_id, payment_missing }], plan[{ from, to, amount }], mine? { paid, share, owed_to_me, returned, i_owe, written_off, over_share, pay_to? }, overrides_invalid }`. `overrides_invalid` — manual totals stopped adding up with purchases (for example, a purchase was deleted) and are ignored: the UI shows a warning. `me` is the owner's id in any "who" field (buyer, lead, share); `saldo` > 0 — owes the lead, < 0 — is owed by them. Event transactions and the journal: deleting a linked payment or transfer in the journal (`delete_transaction`, `delete_transactions`) removes the purchase or settlement from the event; editing the amount and date of a linked transaction (`update_transaction`) rewrites the purchase (the amount, `price_mode: total`, the date; the rate is not recomputed) or the settlement; changing the currency, the transaction kind or the debt direction, and for a settlement — an amount above the debt — is `INVALID_INPUT` ("change it in the event"). Any change to an archived event brings it out of the archive. The `closed` status is when something has been bought and all balances are settled (settlements are not required).

Debts: `get_contact_balances` **adds** to transfers with `debt` the balances of events involving me (the same for a moment in the past — for the net worth history: purchases and settlements dated no later than the moment) (if I lead — each contact participant's balance; if they lead — my balance to them with a sign); transfers created by the event are not included in the sum — the event has already counted them. In analytics (budgets, "Where it went", reports) the event's payment is counted at my share, someone else's purchase as my share from the purchase date, a write-off as spending; `Repay`/`Collect` are not counted as spending.

### workflows — node-based schemes (`crates/app/src/commands/workflows.rs`)

The graph is stored in the vault as JSON (`WorkflowGraph { version, nodes, edges, comments }`), the node catalog is in Rust (`trade_core::workflow::catalog`). A scheme with errors is saved but not turned on. On every tick the scheduler calls `run_due_workflows`: those that have waited out "Wait", schedules (a missed one — at most 12), new transactions (a scheme's own transactions do not run it; transactions of other schemes — only with `include_workflows` / `react_to_workflows`), balance and price threshold crossings, then events (depth ≤ 5). The "Call a workflow" node runs a scheme with the trigger "Called by a workflow" inside the same run (shared transactions, limits and rollback, nesting ≤ 5), the answer is given by "Return a value". Limits: 500 steps and 20 actions per run, 60 runs of a scheme an hour, `max_amount` in `max_amount_currency` (a run that cannot be priced in it is rejected). A failed run rolls back everything it did.

#### How an automation runs (graph v3)

- **Flow and data.** A flow wire defines what runs next; a data wire carries a value. Data is computed lazily, when a node asks for it, and remembered per run (after write nodes and on each loop pass — anew).
- **Order by data.** An action with no incoming flow wire that takes data from other actions (directly or through pure nodes) runs immediately after all of them have run in this pass (`Graph::data_order`). If a source did not run (another "if" branch), it does not run either. Flow is needed only for actions without a result, branches, waits and loops. `validate` warns: `redundant_flow` — the only flow `out → in` repeats a data link; `late_data` — a node reads an action that the flow reaches later. A v2 graph migrates to v3 on load and turns off nodes that would "come alive" under the new rule (before, they did not run).
- **Branches.** Several next nodes are branches (explicit wires and nodes by data). A save point comes before each; an unhandled error in a branch rolls back only it, the others go on, the outcome is `partial { failed }`. An error on the main line rolls back the whole run (`failed`).
- **Errors.** All actions and variable nodes have an "Error" and "Reason" output (except "Stop" and "Return a value"): when connected, it catches a failure without a rollback.
- **Sleep.** "Wait" and "Wait for confirmation" save a `WorkflowWait` with remembered values and a copy of the graph (`graph`): the continuation runs on the graph the run fell asleep on; pure data is recomputed, while "free" nodes run at the end, after the last wait. An answer to a question of a turned-off scheme or over the limit — `INVALID_INPUT`, the question stays. A wait over the limit waits for the next tick; a dropped one (the scheme is off, the node deleted) and a run over 60 an hour go to the journal with the outcome `dropped { reason: off | node_removed | rate_limit }` and do not count toward the limit.
- **The "Queue" node** (`flow.queue`). If a scheme has an enabled "Queue", all firings of one trigger within a scheduler pass (new transactions, missed schedule moments, identical events) give **one** run with `RunContext.batch` (the label `… ×N`, counted as one toward the limit). Nodes before "Queue" see the first firing; "Queue" sets the trigger values, `item`/`index`/`count` for each and passes `each`, then `done`. `mode: sequence` — a failure rolls back the whole run; `independent` — each firing is its own branch (`partial`). "Run"/emulation give a batch of the last up to 3 matching transactions. `validate`: `queue_without_trigger` (an error) and `queue_sleeps` (a wait inside `each`).
- **The confirmation queue** (`queue_mode`) is no longer filled: its role belongs to the "Wait for confirmation" node. The field and the `*_workflow_queued` commands remain for records of old versions.

Invariants of the block:
- **No command creates transactions by itself.** Only `confirm_pending_imports`;
  the background polling (`ExchangeProfile.import_interval_sec` per exchange, `0` = off) puts trades into
  `pending_imports` and sends an event — the user decides.
- The import takes trades, internal transfers (`/v5/asset/transfer/query-inter-transfer-list`) and Earn income (`/v5/earn/yield`); a trade's category is set on request, not guessed from the symbol.
- The key is looked up on the wallet and its parents; someone else's key is not substituted.
- Deduplication by `execId` (`PendingImport.exec_id`; for transfers `transfer:<id>`, for Earn `earn:<id>`), so a repeated import
  and restarts of the background polling create no duplicates.
- Junk trades (no `execId`, unreadable quantity/price, zero
  quantity) are dropped at the boundary and do not reach staging.
- `notice` is a reason code: `no_key` | `unreachable` | `rate_limited` |
  `forbidden_region`. This block throws no errors on network failures.

Commands of this block **do not throw errors** for network failures: they return
an empty list and a `notice` instead. The deal form stays exactly as the user
left it.

- `notice` for `inspect_tx`: `empty` | `unavailable` | `choose_network`.
- `notice` for `bybit_executions`: `no_key` | `unreachable` | `rate_limited` |
  `forbidden_region`.
- `store_id` in `bybit_executions` is optional: if not given — walk up the ancestors
  to the exchange node (Phase N).
- The API secret is never returned: `ExchangeKeyStatus` contains only
  a mask like `abcd…wxyz`.

## Domain types in IPC (important for the UI)

- `Chain` is a union of strings; `Chain`/`ChainInfo` metadata (CoinGecko id, explorer
  patterns) is not passed over IPC but lives in frontend constants (see the model).
- `Amount` in TS is just a `string` (all money fields).
- `StoreKind` — `"exchange" | "hot_wallet" | "cold_wallet" | "bank" | "cash" | "asset" | "liability"`.
- `Transaction` is a union of single-key objects, the key = the transaction kind
  (`{ topup: TopupTx } | { transfer: TransferTx } | …`). On the frontend narrowing is
  via `body(tx, 'topup')` from `src/shared/lib/transactions.ts`; `txLegs(tx)`
  expands a record into signed legs with roles.
- `TxMeta.categories` are category keys; the backend normalizes them (trim,
  lowercase, dedup) and checks that the category exists, is not archived and fits
  by group. A transaction creates no new categories.
- The Bybit exchange category (`spot`/`linear`/`inverse`) is called
  `BybitCategory` in TS, so as not to be confused with `Category`.

## Adding a new command (checklist)

1. The input type in `ipc_contract.rs` (`#[derive(Serialize, Deserialize, TS)]`).
2. An `UnlockedVault` method in `service.rs` + a unit test.
3. A handler in `crates/app/src/commands/<module>.rs` + registration in
   `generate_handler!` (`lib.rs`).
4. `mise run gen-types` → the new type in `src/shared/api/ipc.gen.d.ts`.
5. If the command is async and holds the vault — copy the data before `.await` (rule 3 of AGENTS.md).
