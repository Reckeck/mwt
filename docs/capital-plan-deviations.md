# Расхождения с планом «Капитал»

План: `~/.claude/plans/effervescent-zooming-hickey.md` (ветка `feature/capital`).
Каждое отступление от плана записывается здесь в change того этапа, где оно
возникло (раздел 12 плана).

## 2026-10-21 — этап 0 (J1): правило категоризации у операции не хранится
- **В плане:** раздел 11, п. 11 — аддитивный `TxMeta.rule_id`, группа связей
  «правило, которое категоризовало» у операции.
- **Сделано:** поле не добавлено, группы нет. Карточка категории показывает
  её правила (группа «Правила категорий»).
- **Почему:** `TxMeta` читается и из старого bincode-формата (`FMT_BIN`, v1),
  где поля позиционные: новое поле в `TxMeta` ломает чтение таких файлов.
  Правило 5 запрещает ломать открытие существующих vault.
- **Последствия:** у операции не видно, каким правилом она получила категорию.
  Если понадобится — хранить связь вне `TxMeta` (отдельная коллекция в
  `VaultDoc` по id операции) отдельным этапом.
- **Согласовано:** не требовалось (решение раздела 3 не меняется).

## 2026-10-21 — этап 0 (J1): карточка актива по адресу — общая, не шторка позиции
- **В плане:** раздел 4 J1 — «существующие шторки операции и актива становятся
  видами этой карточки (`?open=tx:id`, `?open=asset:key`)».
- **Сделано:** шторка операции стала карточкой (`?open=tx:id`, связи — в ней же).
  `AssetDetailsSheet` остаётся как есть: она показывает позицию в конкретном
  кошельке. `?open=asset:<key>` открывает общую карточку актива (кошельки,
  оповещения, действия).
- **Почему:** шторка актива привязана к позиции (кошелёк + актив), а адрес
  `asset:key` — к активу вообще; одна шторка на оба смысла путала бы, чей это
  баланс.
- **Последствия:** нет; переход из общей карточки к позиции — через связь
  «Кошельки».
- **Согласовано:** не требовалось.

## 2026-10-21 — этап 0 (J1): «создать связанное» — пока только три диалога
- **В плане:** раздел 4 J1, реестр действий: операция -> автоматизация /
  правило / напоминание; категория -> лимит / сторож расходов; кошелёк -> цель /
  подушка / автоматизация; актив -> оповещение / источник цены; контакт ->
  долг / перевод.
- **Сделано:** цель на счёте кошелька, лимит на категорию (новый пропс
  `category` у `BudgetDialog`), оповещение о цене актива, плюс переходы
  («Операции», «Все лимиты», «Изменить» и т. п.).
- **Почему:** подушка, сторож расходов и источник цены появятся на своих
  этапах (C1, I3, I2); диалоги автоматизации, правила, напоминания и долга
  открываются со своих экранов и пока не принимают подстановку извне.
- **Последствия:** действия добавляются в `shared/lib/entity-actions.ts` на
  этапах, где появляется соответствующая сущность или диалог получает
  подстановку; остаток — в J2.
- **Согласовано:** не требовалось.

## 2026-10-21 — этап 0 (J1): системные уведомления по расписанию оставлены как есть
- **В плане:** раздел 4 J1 — `NoticeRecord.link` в формате `open:kind:id`.
- **Сделано:** формат `open:` у уведомлений о напоминаниях и лимитах в приложении
  (`notifications.rs`); `noticeRoute` понимает `open:…`, путь `/…` и старое
  `имя[:id]`. Ссылки системных уведомлений по расписанию (`notify_snapshot.rs`)
  не тронуты.
- **Почему:** их ссылки приложение не открывает (ОС показывает уведомление без
  перехода), менять нечего.
- **Последствия:** нет.
- **Согласовано:** не требовалось.

## 2026-10-21 — этап 0 (J1): «фильтр по этому» и чипы в строке операции — в J2
- **В плане:** раздел 4 J1 — в контексте фильтра (список операций) основной клик

- **Согласовано:** не требовалось.

## 2026-10-21 — этап 1 (A-core): эталон тестов — формулы, а не calcus
- **В плане:** раздел 11, п. 9 — до A-core снять 4 набора цифр с calcus.ru и
  записать их в тесты.
- **Сделано:** те же 4 набора (без взносов, ежемесячные взносы, квартальная и
  дневная капитализация) проверяются по замкнутым формулам `PV·(1+i)^n` и
  аннуитета, посчитанным с точностью 40 знаков (Python `decimal`), плюс
  простые проценты для «в конце срока».
- **Почему:** калькулятор calcus считает в браузере, запросом его ответ не
  получить; формулы дают точное значение того же расчёта.
- **Последствия:** при ручной проверке на calcus возможны расхождения в копейках
  из-за их округления; если найдутся больше — поправить движок или тест.
- **Согласовано:** не требовалось.

## 2026-10-21 — этап 1 (A-core): ответ `solve` — структура, налог до изъятия
- **В плане:** раздел 4A — недостижимая цель как `SolveOutcome::Unreachable { best }`;
  в порядке шагов месяца налог идёт после изъятия (шаг 6).
- **Сделано:** `SolveResult { reachable, value, input, result }`: при
  `reachable = false` поля описывают лучший достижимый вариант; `input` —
  исходные данные с найденным значением (для обратного режима UI сразу
  показывает этапы с новым взносом). Налог списывается сразу после
  капитализации, до взносов «в конце месяца» и изъятия. Добавлены
  `InvestResult.invested` и `InvestYear.invested` (начальная сумма + взносы) для
  графика «вложено / проценты».
- **Почему:** одна форма ответа проще для TS, чем тегированный enum; налог с
  уже начисленных процентов не должен зависеть от того, успело ли изъятие
  опустошить счёт.
- **Последствия:** нет.
- **Согласовано:** не требовалось.
